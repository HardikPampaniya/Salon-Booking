# API reference

All routes are under /api. Errors use an error object with a code and message. Customer booking and management responses require the private booking management token; there is no public booking-list or admin endpoint.

## Public endpoints

| Method and path | Purpose |
| --- | --- |
| GET /api/health | Sanitized database, payment, and booking status. |
| GET /api/booking/readiness | Non-secret setup issues and whether a hold/payment can be created. |
| GET /api/config | Public salon profile, opening hours, and timezone. |
| GET /api/services | Service catalog and category groups. |
| GET /api/availability?serviceId=id&date=YYYY-MM-DD | Arrival times for one service. |
| GET /api/availability?serviceIds=id1&serviceIds=id2&date=YYYY-MM-DD | Arrival times for a cart. |

Availability uses salon local time and the configured opening hours. It returns one-hour arrival windows and removes a window already held or confirmed by another booking. It does not use service duration, staff schedules, breaks, or employee selection. A selected window is when the customer plans to arrive; it does not promise the service starts then. The default booking horizon is 60 days. While BOOKING_ENABLED is false, the API may display arrival options, but the server will not reserve them or create payment orders.

Only active services with menuSelectable=true, approved wording/details, and a positive final price can be checked out. Flagged services and percentage-only offers without an exact final price remain blocked.

## Create a booking hold

### POST /api/bookings/holds

Creates a temporary 10-minute hold on the selected one-hour arrival window and a Razorpay order for exactly INR 100. A unique arrival lock prevents a second active booking for the same date and window. Requires an Idempotency-Key with 16-100 characters.

Request body:

~~~json
{
  "serviceIds": ["service-id-from-catalog"],
  "date": "YYYY-MM-DD",
  "startAt": "ISO-8601 arrival-window start returned by availability",
  "name": "Customer name",
  "phone": "+91 9876543210",
  "gender": "male",
  "age": 28,
  "managementToken": "32-byte random token generated by the browser",
  "policyAccepted": true
}
~~~

The API accepts 1-20 distinct service IDs (and the earlier single serviceId form for compatibility). The server calculates the service subtotal and fixed advance; it ignores browser-submitted prices. The response includes the Razorpay public Key ID/order ID/amount, booking details, customer details, and private management token. Never log or share the token.

Possible errors include BOOKING_NOT_READY, SALON_CONFIGURATION_INCOMPLETE, ARRIVAL_TIME_UNAVAILABLE, IDEMPOTENCY_KEY_REUSED, and PAYMENT_ORDER_UNAVAILABLE.

## Payment confirmation and management

### POST /api/bookings/verify-payment

Accepts Checkout's order ID, payment ID, and signature. The server validates the checkout HMAC, fetches payment state from Razorpay, and matches order, amount (10,000 paise), and currency (INR). A booking is confirmed only after trusted capture verification.

### POST /api/bookings/manage

Returns one booking's status with its reference and Authorization: Bearer <managementToken>. It returns services, arrival date/time, customer details, payment/refund state, and cancellation eligibility. The token is random and stored hashed.

### POST /api/bookings/cancel

Uses the same private token. Customer cancellation is allowed until 60 minutes before arrival. A qualifying cancellation releases the arrival lock and requests a refund of a captured advance to the original payment method. Refund status remains pending until Razorpay confirms it; uncertain outcomes require manual review. Rescheduling is not implemented.

## Razorpay webhook

### POST /api/webhooks/razorpay

Receives the exact raw JSON body and validates X-Razorpay-Signature using RAZORPAY_WEBHOOK_SECRET. Event IDs are deduplicated. Subscribe to payment.authorized, payment.captured, payment.failed, refund.processed, and refund.failed. Use separate Test and Live webhooks/secrets. See RAZORPAY_SETUP_GUIDE.md for setup steps.

## Notifications

WhatsApp messages are not currently enabled or sent. The site shows the verified booking result after payment, and stores the customer's name, phone, gender, and age for the later owner/customer messaging setup. Do not treat a queued or mocked notification as delivered.

## Important states

- Booking: held, confirmed, cancelled, expired, manual_resolution.
- Payment: order_pending, order_creating, created, authorized, captured, failed, refund_pending, refunded, refund_failed, manual_review.
- Refund: pending, submitting, processing, processed, failed, manual_review.
- Notification: pending, sending, accepted, mocked, manual_review. accepted means a provider accepted the request, not that it reached a recipient; mocked means no message was sent.

The public booking gate remains off until the full readiness report is clear and the salon owner approves launch.
