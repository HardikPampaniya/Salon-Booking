# API reference

All endpoints are under `/api`. JSON errors use `{ "error": { "code": "...", "message": "..." } }`. Responses containing customer booking state are `no-store` and require the booking’s secret management token. There are no public booking-list or admin endpoints.

## Public endpoints

| Method and path | Purpose |
| --- | --- |
| `GET /api/health` | Sanitized API, database, payment, and booking readiness. |
| `GET /api/booking/readiness` | Lists non-secret setup conditions that keep checkout disabled, such as database, payment, notification, policy, or menu setup. Service durations and staff rosters are not required. |
| `GET /api/config` | Public salon identity, hours, and timezone. |
| `GET /api/services` | Configured service list and prices. |
| `GET /api/availability?serviceId=service-id&date=YYYY-MM-DD` | Future 15-minute arrival times during salon hours for that service/date. The selected time is for arrival, not a guaranteed service start. |

Arrival times use the salon timezone and exclude already reserved/held arrival times when MongoDB is connected. The date must be within `MAX_BOOKING_DAYS_AHEAD` (60 days by default). When MongoDB is disconnected, the API can still show schedule-based choices but cannot know which times are reserved; checkout remains disabled, so those choices are not a reservation. After closing, there are no later times that day; the client defaults to tomorrow.

## Booking endpoints

### `POST /api/bookings/holds`

Creates one 10-minute hold for a cart containing 1-20 distinct services and one 15-minute arrival time, then creates a single Razorpay order for the fixed INR 100 advance for that visit. The server stores a price snapshot for each service and calculates their combined total; the service starts when a team member is available. No employee assignment or service-duration check is used. Requires an `Idempotency-Key` header (16-100 characters).

```json
{
  "serviceIds": ["service-id-from-catalog", "another-service-id"],
  "date": "YYYY-MM-DD",
  "startAt": "ISO-8601 timestamp returned by availability",
  "name": "Customer name",
  "phone": "+91…",
  "email": "optional@example.com",
  "managementToken": "32-byte random token generated by the browser",
  "policyAccepted": true
}
```

`serviceIds` must contain 1-20 distinct service IDs from the catalog. For backwards compatibility, the server also accepts the earlier single `serviceId` field. The server calculates the combined service total and the one advance; it ignores any client-supplied amount. `startAt` must be a future arrival time returned for the selected date. A successful response includes the Razorpay public key ID and order ID, plus the private management token. Do not log or share that token.

Errors include `BOOKING_NOT_READY`, `ARRIVAL_TIME_IN_PAST`, `OUTSIDE_OPENING_HOURS`, `IDEMPOTENCY_KEY_REUSED`, and `PAYMENT_ORDER_UNAVAILABLE`. A conflict means the customer must choose another currently offered arrival time.

### `POST /api/bookings/verify-payment`

Accepts Razorpay Checkout's `orderId`, `paymentId`, and `signature`. The server verifies the HMAC, fetches payment status directly from Razorpay, and checks order ID, amount, and currency. Only a captured payment confirms an active hold.

### `POST /api/bookings/manage`

Returns one booking’s status when the request includes its `reference` and `Authorization: Bearer <managementToken>`. The response includes `booking.cancellationAllowed`, which becomes false inside the one-hour cutoff. The token is random, stored hashed, expires after 180 days, and is not included in status responses.

### `POST /api/bookings/cancel`

Uses the same private token. Cancels a held or confirmed booking and releases its arrival time. If the INR 100 advance was captured, the server creates a locally idempotent refund request and submits it once to Razorpay. The response keeps refund state separate; it does not describe a refund as complete until a provider response or webhook confirms `processed`.

Customer cancellation is permitted when the selected arrival time is at least 60 minutes away. A request inside the final hour returns `CANCELLATION_WINDOW_CLOSED`; the customer should contact the salon. Rescheduling is not implemented. The privacy and booking policy versions must be approved before public booking is enabled.

## Provider webhook

### `POST /api/webhooks/razorpay`

Receives the raw JSON body and checks `X-Razorpay-Signature` against `RAZORPAY_WEBHOOK_SECRET`. Replayed event IDs are deduplicated. Configure these events in Razorpay:

- `payment.authorized`
- `payment.captured`
- `payment.failed`
- `refund.processed`
- `refund.failed`

The app supplements Checkout verification with webhooks so a closed browser does not prevent payment reconciliation. Webhook events are not used as proof unless their signature is valid.

## State fields

Booking state (`Booking.status`): `held`, `confirmed`, `cancelled`, `expired`, `manual_resolution`.

Payment state (`Payment.status`): `order_pending`, `order_creating`, `created`, `authorized`, `captured`, `failed`, `refund_pending`, `refunded`, `refund_failed`, `manual_review`.

Refund state (`Refund.status`): `pending`, `submitting`, `processing`, `processed`, `failed`, `manual_review`.

Notification state (`Notification.status`): `pending`, `sending`, `accepted`, `mocked`, `manual_review`. `accepted` means the Resend API accepted a request, not that the recipient received it. `mocked` explicitly means no email was sent.

An uncertain refund API result moves to manual review and is not automatically resubmitted. Verify the refund in Razorpay before any manual retry. This avoids creating a second refund when a provider accepted a request but the response was lost.
